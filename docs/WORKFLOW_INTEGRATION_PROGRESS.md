## 2026-09-09：对齐前加签、后加签与减签状态机

### 本次更新

- 按芋道 `BpmTaskSignTypeEnum` 和 `BpmTaskStatusEnum` 对齐前加签、后加签的运行时语义，并新增任务状态 `WAIT = 0`、`RUNNING = 1`；加签类型改为写入 Flowable 任务 `scopeType`，同时兼容此前以 `workflow-sign:*` 写入 `category` 的运行中任务。

- 后加签时，新建子任务只保存 `owner` 并进入 `WAIT`。原审批人点击通过后，原任务不立即完成，而是进入 `APPROVING`，保存审批意见、签名、附件和下一节点变量，再激活全部后加签子任务；最后一个子任务通过后才完成原任务并推动流程继续。
- `APPROVING` 父任务在后加签处理期间拒绝重复通过或拒绝，详情页隐藏普通审批按钮并显示“等待后加签任务完成”的状态提示，避免流程被重复推进或反向结束。

## 2026-09-09：HTTP 回调触发器等待与续跑接口

### 本次更新

- HTTP 回调触发器现在由两段组成：先执行“发起 HTTP 请求”的 ServiceTask，再进入“HTTP 回调等待”ReceiveTask，流程会停在该等待节点直到外部回调。
- ServiceTask 发出的请求体自动携带 `processInstanceId` 和 `taskDefineKey`；`taskDefineKey` 即等待节点 ID，外部业务拿到后回调本平台即可续跑。
- 新增后端接口 `PUT /bpm/task/trigger-callback?processInstanceId=xxx&taskDefineKey=xxx`，通过 `runtimeService.trigger` 触发 ReceiveTask 并继续后续节点。
- 触发器 JavaDelegate 不再对 HTTP 回调静默放行；配置缺失 URL 时不会继续产生“假通过”。

### 验证说明

- 本轮后端改动尚未重新编译；编译将在下一步完成后统一执行并重启。
- 后续人工验证：配置一个 HTTP 回调触发器指向本地测试接收端，确认收到 `processInstanceId/taskDefineKey`；再调用 trigger-callback 后流程继续到下一节点。

### 已知差距与风险

- 回调接口当前按平台权限控制，外部业务调用时需要携带可访问 token；正式部署如需开放白名单，需要在安全评审后配置。
- 等待节点目前没有独立超时设置；若外部业务一直不回调，流程会永久等待。

## 2026-09-09：撤回时显式收敛活动任务状态

### 本次更新

- 撤回已办任务时，会先遍历流程实例当前活动任务，把本次要随活动跳转一起撤掉的任务显式标记为“已取消”，原因统一为“前一节点撤回”。
- 之后再执行 `moveActivityIdsToSingleActivityId` 回到撤回任务节点；即使 Flowable 取消事件没有把每个活动实例都完整落到历史，时间线也能看到被撤回任务不再是“审批中”。
- 显式标记不会覆盖已完成的终态任务；对已经处于已通过/已拒绝/已退回/取消等终态的任务不做重复覆盖。

## 2026-09-09：补齐审批超时边界事件与自动处理

- 超时处理调用现有“系统自动完成”入口，不依赖 Shiro 登录用户，因此 Flowable 异步定时任务场景也能执行。
