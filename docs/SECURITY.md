# 安全规范

## 1. 适用范围

本规范覆盖后端、前端、数据库、文件上传、AI/外部服务配置以及单体/微服务部署。它是开发基线，不替代组织的合规、隐私和应急制度。

## 2. 漏洞报告

不要在公开 Issue、提交信息、日志或截图中披露可利用细节、生产地址、用户数据或密钥。发现疑似漏洞时：

1. 停止进一步传播或利用；
2. 记录受影响版本、入口、最小复现、影响和建议缓解措施；
3. 通过项目维护者指定的私密渠道报告；若仓库尚未公布渠道，先联系仓库管理员建立私密沟通；
4. 泄露凭据应立即吊销/轮换，并审计使用记录；
5. 修复发布前避免公开完整利用步骤。

本仓库当前没有声明固定安全邮箱，禁止编造联系人或响应时限。

## 3. 身份认证与会话

- 当前主干采用 Shiro + JWT，并依赖 Redis 支撑会话/在线状态；不要混用官网其他分支的 Sa-Token 或 Spring Authorization Server 注解。
- 登录、验证码、短信、第三方登录和 SSO 改动必须考虑重放、爆破、账号枚举、Token 生命周期和登出失效。
- Token 只通过项目统一客户端/过滤器传递；不写入 URL、日志、错误消息或分析事件。
- Cookie 场景应设置合适的 `HttpOnly`、`Secure`、`SameSite`，生产环境强制 HTTPS。
- 认证白名单采用最小集合；新增匿名接口必须有明确理由、输入限流和测试。

## 4. 授权与数据隔离

前端菜单和按钮只提供可见性，不构成安全控制。每个敏感后端操作必须进行服务端授权：

- 使用 `@RequiresPermissions`/`@RequiresRoles` 声明功能权限；权限标识与菜单按钮一致。
- 查询列表根据业务使用 `@PermissionData`，并测试普通用户、跨部门、跨租户和管理员场景。
- 获取、修改、删除单个对象时校验对象归属，不能只依赖“ID 存在”。
- 批量接口逐项或按安全条件限制范围，防止通过 ID 集合越权。
- 多租户模式下，租户 ID 来自可信认证上下文；不能信任前端任意指定的租户头。
- 管理员、导出、导入、数据源和 Online 自定义 SQL 等高权限能力应单独授权和审计。

迁入的 `jeecg-boot-module-project` 保留了旧系统的接口契约，但旧实现尚未系统补齐按钮权限、对象归属、部门数据范围和租户隔离。部署到共享或生产环境前，必须逐个 `/project/**` 接口完成授权建模和越权测试。当前 BPMN 还沿用旧系统的 `admin` 办理人以保持迁移兼容，正式启用审批前必须替换为组织确认的候选用户/角色表达式。

## 5. 输入、SQL 与输出

- 使用 Bean Validation 和业务校验限制长度、格式、范围、枚举和集合大小。
- Mapper 使用参数绑定。不得拼接用户控制的 SQL、排序字段、列名、表名、数据源名或自定义条件。
- 确需动态标识符时使用服务端白名单映射，不把客户端字符串直接放入 SQL。
- 分页上限、导出上限和复杂查询应受限，避免资源耗尽。
- 错误响应使用通用消息，不返回堆栈、SQL、文件路径、内部主机或下游响应中的秘密。
- 前端展示富文本、Markdown、外链和服务端错误时采用已有 XSS 清理/白名单；避免 `v-html` 直接渲染不可信内容。

## 6. 文件上传与下载

无论使用本地、MinIO 还是 OSS：

- 同时校验大小、扩展名、MIME 和必要的文件特征；客户端校验不能代替服务端校验。
- 服务端生成对象键/文件名，规范化路径并阻止 `..`、绝对路径和双重扩展名绕过。
- 上传内容与应用执行目录隔离；默认不允许脚本、HTML、可执行文件或服务端模板。
- 下载/预览接口校验对象权限、租户和有效期；私有对象使用短时签名 URL。
- 记录安全审计元数据，但不要记录文件正文和敏感个人信息。
- 可行时增加恶意文件扫描和图片重编码。

官方上传入口和存储切换说明见 [统一文件上传规则](https://help.jeecg.com/java/upload/config/)。

## 7. 密钥与配置

禁止提交：

- 数据库/Redis/Nacos/对象存储真实密码；
- JWT、缓存加密、签名或 SSO 密钥；
- DeepSeek/OpenAI 等模型 API Key；
- 私钥、证书私钥、Webhook Secret、云凭据；
- 生产域名、内网拓扑和可识别个人的数据样本（除非已批准公开）。

要求：

- 本地配置使用被忽略的覆盖文件或环境变量；生产使用密钥管理系统。
- 文档和示例使用 `<YOUR_SECRET>` 等明显占位符。
- 所有前端 `VITE_*`/`VITE_GLOB_*` 均视为公开，不能保存秘密。
- 各环境使用独立凭据，权限最小化，定期轮换。
- 发现历史提交包含密钥时，先吊销轮换，再评估清理 Git 历史；删除当前文件不足以消除泄露。

## 8. 依赖与供应链

- 依赖升级必须说明原因、兼容性和安全影响，更新对应锁文件/POM，并运行测试。
- 不从未知镜像、临时网盘或未验证脚本安装依赖。
- CI 使用锁定依赖；前端保留 `pnpm-lock.yaml`，不要混入其他包管理器锁文件。
- 定期检查 Maven、pnpm、容器镜像和基础镜像漏洞；高危问题优先修复或记录缓解措施。
- 构建日志和制品不得包含环境文件、源码密钥或调试转储。

## 9. 部署与网络

- 生产强制 HTTPS；Nacos、Redis、MySQL、监控和任务控制台不直接暴露公网。
- 替换 Compose 中的示例密码，关闭不需要的端口和服务，使用最小权限账号。
- CORS 指定可信来源、方法和 Header；不要在携带凭据时使用通配符。
- 网关、登录、上传、导出、短信、AI 和昂贵查询配置限流与超时。
- 生产关闭详细调试、Swagger/管理端公开访问和默认账号；保留必要审计日志并设置保留周期。
- 备份需加密且定期恢复演练；数据库破坏性迁移必须先备份并准备回滚。

## 10. AI 与外部服务

- 发送给模型、地图、搜索、短信、邮件或对象存储的数据属于对第三方的数据传输；确认业务合法性、用户授权和最小必要性。
- Prompt、知识库和工具返回均是不可信输入，不能据此执行 SQL、文件操作、网络调用或权限变更。
- 不把系统提示词当作秘密保护机制；真正的密钥和授权必须由服务端控制。
- 对模型输出进行结构校验、长度限制、内容安全检查和人工确认，尤其是会触发外部副作用的场景。

## 11. 安全评审清单

- [ ] 是否新增/变更认证或匿名入口？
- [ ] 是否校验功能权限、对象归属、数据权限和租户边界？
- [ ] 是否存在 SQL/命令/模板/路径/URL 注入？
- [ ] 是否处理上传、富文本、导入导出或外部回调？
- [ ] 是否新增秘密、个人数据、日志或第三方数据传输？
- [ ] 是否有限流、超时、分页/批量上限和错误收敛？
- [ ] 是否增加负向测试与回滚方案？
