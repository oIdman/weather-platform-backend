# 项目目标

## 1. 项目定位

本仓库当前定位为：基于 JeecgBoot 3.9.5 的企业应用开发基线，在保留低代码、权限、数据管理、报表、AI 扩展以及单体/微服务切换能力的同时，为后续明确的业务需求提供可维护的前后端工程。

项目追求“平台复用 + 清晰业务边界”，而不是直接修改大量平台核心代码。简单功能可通过 Online 配置或代码生成器提效，复杂业务必须沉淀为可测试、可审查的源码模块。

## 2. 当前状态

已具备：

- JeecgBoot 平台前后端源码和初始化数据库；
- 用户、角色、菜单、按钮权限、数据权限、字典等基础能力；
- Vue 3 管理前端及动态路由/菜单；
- 单体与 Spring Cloud 两种运行结构；
- Docker Compose、本地构建和多环境配置；
- Online/代码生成、报表、AI/RAG 等平台扩展基础。

尚未由仓库事实定义：

- 具体行业、用户角色和业务流程；
- “天气”相关数据源、接口、页面、告警、预测或产品范围；
- 业务级 SLA、数据保留、合规和部署规模。

虽然工作区路径和少量空目录包含 `weather` 名称，但目录目前没有可提交业务源码。它只能视为预留意图，不能作为实现依据。任何 Agent 或贡献者都不得自行补全产品假设。

## 3. 近期目标

### G1：建立可理解的工程基线

- 新开发者在较短时间内能定位前端、后端、单体、微服务和数据库模块。
- 文档给出可复制的开发、构建、验证和安全规则。
- 仓库版本事实与上游最新文档的差异有明确说明。

验收：根目录规范文档和 `docs/` 文档完整、链接有效、命令与构建文件一致。

### G2：明确业务再编码

在新增天气或其他业务前，维护者应至少明确：

- 目标用户和核心使用场景；
- 数据来源、更新频率、授权和失败策略；
- 核心实体、权限模型、租户/组织隔离；
- 单体模块还是独立微服务的选择依据；
- API、页面、报表/告警和验收指标；
- 隐私、安全、合规、可用性和成本约束。

验收：形成可测试的需求或 ADR，再创建领域模块。

### G3：保持可升级性

- 业务代码尽量放在独立模块，减少对 Jeecg 核心的侵入。
- 平台升级与业务功能分开提交，先阅读升级说明并验证数据库迁移。
- 生成代码经过人工合并，不直接覆盖手工实现。

验收：平台升级可以通过清晰差异完成，业务模块边界不依赖隐式核心改动。

## 4. 设计原则

1. 单体优先：没有独立伸缩或隔离需求时，优先单体，降低运维复杂度。
2. 权限内建：功能权限、对象归属、数据权限和租户隔离从需求阶段设计。
3. 数据可信：外部数据必须记录来源、时间和不确定性，不伪造实时信息。
4. 最小改动：扩展业务模块，不随意改平台核心；不为未来场景预先抽象。
5. 自动验证：核心业务规则、权限和数据转换应有测试；生成代码也不例外。
6. 安全默认：不提交密钥，最小暴露端口，第三方数据传输最小化。
7. 文档同步：模块、配置、命令、迁移或运行方式变化时同步更新 `docs/`。

## 5. 非目标

- 不承诺当前仓库已经是完整产品。
- 不默认启用所有微服务、AI、消息队列或多数据库能力。
- 不以 Online 配置替代所有复杂领域逻辑。
- 不为了追随官网最新版而无计划升级依赖。
- 不把前端按钮隐藏当作安全控制。
